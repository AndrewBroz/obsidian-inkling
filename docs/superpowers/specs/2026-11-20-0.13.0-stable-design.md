# 0.13.0 stable: resolve removes, code is not markup, conservative cleanup — Design

**Status:** approved, 2026-11-20.

0.13.0-beta.0 shipped Release A of `2026-10-12-inklingmarkup-metadata-attributes-design.md` (reads
trailing `{author=…}` blocks, writes legacy `@@` by default). The team needs to update to it, so it goes
stable as **0.13.0**, carrying three user-experience changes with it so the release the team installs
already has them.

## Intent

Inkling is used by a small team whose notes sync between machines. Four irritations:

1. Resolving a comment leaves it in the note; users expect resolve to make it go away.
2. `@@` metadata collides with citation/author `@` syntax in other plugins. Already solved by the
   attribute-block syntax; what remains is getting the team onto a version that reads it.
3. Sync leaves broken CriticMarkup fragments in notes. Only Inkling writes CriticMarkup (users don't
   type it by hand), so an unpaired delimiter is debris, not a half-typed range.
4. CriticMarkup inside code is parsed. Verified 2026-11-20: `getRangesInText` returns ranges inside
   fenced blocks and inline code spans, so Accept All / Reject All rewrite code samples.

## Goals

- **G1** `remove_on_resolve` is on for every install, new and existing — once. A user who turns it off
  afterwards stays off.
- **G2** 0.13.0 stable = beta.0 + G1 + G3 + G4. Writer default stays `legacy` (Release B is deferred
  until the team is confirmed on 0.13; out of scope here).
- **G3** No CriticMarkup range is recognised whose opener lies inside a fenced code block, on any path
  (editor state, reading view post-processor, vault index/worker, original-text API).
- **G4** Broken markup fragments are cleaned from a note when it is opened, when an open note changes
  from outside the editor (sync), and on demand — removing only delimiter characters, never words.

## Non-goals

- Release B / C (writer default flip, switch notice).
- A vault-wide background sweep that rewrites unopened notes.
- **Inline code spans** (Claude's call after review): backticks are common inside suggestions and
  comments (`{++ run `npm i` ++}`), and a suggested deletion of one backtick would pair with a later one
  and hide real ranges. The user asked about code *blocks*; inline spans stay as today.
- Indented (4-space) code blocks: ambiguous with nested list content in Obsidian; not treated as code.
- Cleaning anything ambiguous: a lone `~>`, braces that don't parse as an attribute block, unknown
  JSON before `@@`.

## Anti-goals (failure even if it "works")

- Cleanup deletes or moves any word the user wrote.
- Cleanup touches text inside code, or inside any valid range (including comment bodies).
- Cleanup fights sync: repeated rewrite loops, or edits to a file the user isn't looking at.
- A user who deliberately turns remove-on-resolve off gets it switched back on.

## Approaches

### Code exclusion (G3)

| Option | Trade-off |
|---|---|
| **A. Filter at the parser (picked)** | One change in `cursorGenerateRanges` covers all paths. Must handle a grammar range that starts in code and pairs with a closer outside. |
| B. Mask code before the grammar | Cleanest semantics, but breaks incremental parsing: opening/closing a fence changes masking far below the edit, defeating fragment reuse in `range-state.ts`. |
| C. Use Obsidian's Markdown syntax tree | Only exists in the editor; misses reading view, worker index and API. |

User picked **A** (2026-11-20).

### Cleanup trigger (G4)

| Option | Trade-off |
|---|---|
| **On open + on external change of an open note + command (picked)** | User sees the change, it's one undoable transaction. Unopened notes stay dirty until opened. |
| Periodic vault sweep | Catches everything, but silently rewrites files nobody is looking at and can race sync. Rejected as not conservative. |
| Command only | Safest, but doesn't meet "periodically clean". |

User asked for **conservative**; trigger choice is Claude's call within that.

## Design

### G1 — remove on resolve for everyone

- `DEFAULT_SETTINGS.remove_on_resolve = true`.
- New one-time migration modelled on `disableDiffGutterOnce` (`src/constants.ts:158`):
  `enableRemoveOnResolveOnce(settings, saved)` — if `saved` exists and lacks
  `remove_on_resolve_migrated`, set `remove_on_resolve = true` and the flag. Called from
  `migrateSettings` on every load next to `disableDiffGutterOnce`, persisting immediately when it fires.
  New installs get the default and the flag.
- Settings description updated: mention the "Remove resolved comments in this note" command for
  cleaning up threads resolved before the switch.

### G3 — code is not markup

- New pure module `src/editor/base/edit-util/code-regions.ts`:
  `findCodeRegions(text): {from, to}[]` (sorted, non-overlapping). CommonMark-faithful enough for
  Obsidian:
  - fenced blocks: a line starting (≤3 spaces indent) with ≥3 `` ` `` or `~`; closes on a line with a
    fence of the same character and ≥ the same length; an unclosed fence runs to end of text. Also
    fences inside blockquotes/callouts (`> ```…`).
  - a closing fence line may be followed by a CriticMarkup closer (```` ```++} ````), so a suggested
    or highlighted code block doesn't leave its fence unclosed to end of document.
  - Frontmatter is not code (unchanged behaviour).
- `cursorGenerateRanges` drops any range whose **opener** lies inside a fenced region. If such a range
  ends outside the region, parsing resumes at the region's end using the existing malformed-range
  resume path (`range-parser.ts:88-140`), so it can't swallow real ranges after the block. A range whose
  opener is in prose is kept even if it covers fence lines (e.g. a suggestion that adds a code block).
- Incremental path (`range-state.ts`): dirty spans must be widened to the whole document when an edit
  inserts/removes a fence line or changes a backtick count within the span such that region boundaries
  shift. Simplest acceptable rule: if the edit touches a line containing ``` or ~~~, or changes the set
  of code regions intersecting the dirty span, regenerate from the earliest affected region start to
  document end. Builder may choose a cheaper exact rule if tests prove it.
- Code regions are computed over the full document text; cache by document identity in the editor
  state field to avoid recomputing per span.
- *(Superseded by the 2026-11-21 addendum below.)* Suggest mode: an edit lying **entirely** inside a fenced region passes through untracked. An edit that
  crosses a fence boundary is tracked as today (its opener lands in prose, so it stays parsed). Comment
  mode: a comment whose anchor would start inside a fenced region is refused with a Notice ("Comments
  can't be added inside code blocks").
- Reading view: post-processor relies on `getRangesInText`; additionally skip `<code>`/`<pre>`
  elements so a range string inside rendered code is never decorated.

### G4 — conservative cleanup

**Debris** = any of the following that lies outside every range **as the grammar pairs them without
the G3 code filter**, and outside every fenced region. Using the unfiltered parse means a range G3
ignores is never mistaken for debris; the two features can't compound into deleting markup.

1. an opener token `{++` `{--` `{~~` `{==` `{>>`;
2. a closer token `++}` `--}` `~~}` `==}` `<<}`;
3. an attribute block (per `parseAttrBlock`) not attached to a range closer, whose keys are all Inkling
   keys **and** which contains `author` or `time` (or `a`/`t`). A lone `{style=…}` or `{color=red}` may
   belong to another plugin's attribute syntax and is left alone;
4. `{json}@@` where `parseLegacyMetadata` accepts the JSON, not inside a range.

**Repair** removes exactly the debris characters. All text between debris stays. One pass, then
re-parse; if the re-parse yields new debris (e.g. removing an opener exposed something), repeat up to 3
passes, then stop.

**Never:** inside code, inside a valid range (comment bodies may contain `<<}`-like text only if the
grammar already treats them as content), a lone `~>`, unrecognised braces.

**Triggers:**

- `file-open` / becoming active, for a Markdown note in an editor (live preview or source), after the range state field
  has parsed it.
- The **active** editor's document replaced by an external change (Obsidian reloads file content
  after a vault `modify` not originating from this editor). Background tabs and the unfocused side of a
  split are cleaned when they next become active. Debounce 2 s; if the user typed in the last 2 s, the
  run is rescheduled (not dropped) until 2 s of idle.
- Command **"Clean up broken markup in this note"** — always runs, reports "No broken markup found"
  when clean.
- Setting **"Clean up broken markup automatically"** (default on) gates the first two.

**Application:** one CM6 transaction tagged with the plugin-edit annotation (so suggest mode doesn't
wrap it) and `addToHistory: true` (undoable). Notice: "Inkling cleaned N broken markup fragment(s).
Undo to restore." Never writes files that aren't open in an editor. No-op when nothing found, so no
loop: a cleaned document has no debris, and a re-trigger produces no transaction.

**Module:** `src/editor/base/edit-logic/cleanup.ts` — pure `findDebris(text, ranges, codeRegions):
{from, to, kind}[]` and `cleanupChanges(...)`; trigger wiring in a small editor extension.

## Testing

- `code-regions` unit tests: fences (``` / ~~~, longer closers, unclosed, blockquote), inline spans
  (multi-backtick, unmatched, across blank line), mixed.
- Parser tests: ranges in fenced/inline code ignored on all four entry points; opener-in-code paired
  with closer-in-prose doesn't swallow later real ranges.
- Incremental: fuzz (extend `range_state_fuzz`) typing/removing fence lines; incremental result must
  equal a full re-parse.
- Cleanup: table of debris cases → expected text; property test that cleanup never changes the
  sequence of non-delimiter characters outside removed debris (i.e. the output equals the input with
  only debris spans deleted) and never touches code or valid ranges; idempotence.
- Settings migration: existing save without flag → on + flag; save with flag and `false` → stays off.

### Existing ranges inside code blocks

**Decided (2026-11-20):** no migration or finder command. The team has no suggestions or comments
inside code blocks today. The README upgrade note says that markup inside fenced code blocks is no
longer recognised, so any pending change there should be accepted or rejected before updating.

## Release

After implementation and green suite: `bun run release-minor` promotes `0.13.0-beta.0` → `0.13.0`;
push the tag alone (see release memory: never batch tags). README upgrade note: resolve now removes
comments by default; code blocks are no longer parsed; automatic cleanup and its setting.

## Addendum (2026-11-20): simplified fence handling — supersedes the G3 suggest-mode rules above

*The Suggest-mode rules and the comment rule in this addendum are superseded by the 2026-11-21 addendum below; its
parsing rules (plain CommonMark regions) still hold.*

Several review rounds showed that letting Suggest mode write CriticMarkup on or around fence lines needs an
open-ended set of special parsing forms (`{--```--}` as a fence, trailing openers/closers on fence lines,
"no unclosed block" disambiguation, reading-view re-rendering). **Decided (user, 2026-11-20): simplify.**

### Rule: CriticMarkup never sits on a fence line or inside code

**Code regions are plain CommonMark.** A fenced block is exactly what CommonMark (and Obsidian) says it is:
``` or ~~~ fences, ≤3 spaces indent, inside `>` quotes / list indentation, same char and ≥ length to close,
unclosed → end of text (or the end of its quote or list item). No CriticMarkup-aware forms: a line like `{++````
is not a fence (it starts with `{`), and ```` ```++} ```` is an *opening* fence whose info string is `++}`, exactly as
CommonMark and Obsidian read it, so a block that 0.12 wrote as `{++```js … ```++}` leaves the rest of the note as code
until its markers are moved onto lines of their own (README upgrade note).
The parser ignores ranges whose opener is inside a region (unchanged), and the editor rebuilds when regions
move (unchanged). Reading view uses the same rule with no special re-rendering.

**Suggest mode, per change:**
1. **Inside a code block** — content, info string, or typing that keeps fence lines intact: applied plainly
   (untracked).
2. **Prose only** (touches no fence line or code): tracked exactly as before.
3. **Whole code blocks added or removed together with prose** (a paste containing complete blocks; a
   selection covering complete blocks): tracked, but every opener/closer is placed on a prose line — never
   on a fence line, never in code. A range may span lines and contain whole blocks
   (`intro{++\n```js\ncode\n```\n++}`, `prev{--\n```\nx\n```\n--}next`). Where no prose line is
   available to carry the marker, use the smallest adjustment that keeps markers on prose lines; if none
   exists, refuse the change with a Notice.
4. **Fence lines are protected** (the earlier "Protect the fence" decision): typing at the start/indent/quote
   prefix of a fence line goes onto its own line (carrying the prefix); a Backspace/Delete or partial
   selection that would break or merge a fence line is widened to whole blocks (then rule 3) or refused with a
   Notice.
5. Multi-cursor: each change is decided independently; no keystroke is dropped except an explicit rule-3/4
   refusal, which shows a Notice.

**Comments** are refused when their anchor or insertion point would land on a fence line or in code
(unchanged behaviour, simpler predicate).

**Cost accepted:** edits inside code blocks are never suggestions (they never were — markup in code was the
bug). Literal CriticMarkup shown inside a code block is just code.

**Goal for the implementation:** the fence-related source added on this branch shrinks from ~1,250 lines to
roughly 250; `fence-guard.ts`'s option machinery, `closerFollows`, `head_end`/wrapped-fence forms, the
"no unclosed block" logic and the reading-view re-render are removed, not reworked.

## Addendum (2026-11-21): fence handling on trust — supersedes the Suggest-mode rules above

**Decided (user, 2026-11-21): maximum simplicity; Inkling trusts the user.** In Suggest mode, a change that touches a
code block — its content or any fence line, `[region.from, region.to]` in the document before the change — or inserts
a fence-shaped line is applied exactly as typed, untracked. Every other change is tracked as before. With several cursors this is decided per change.
There are no refusals, notices, widening, moved text or own-line forms: a user who breaks a fence breaks it. Adding a
comment with either end of the selection in a code block is refused with a notice, and the comment pill is hidden
there; comment placement and threads are otherwise unchanged. The parsing rules (plain CommonMark regions, ranges
opened in code ignored, rebuild when regions move, reading view) are unchanged.
